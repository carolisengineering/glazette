# Sync Across Devices Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Carol signs in with an email code from an Account button on the shelf, only allow-listed emails get a code, and turned-away attempts are recorded. This plan details that first PR (S1) and outlines S2–S4, which get their own detailed plans once S1 has merged and its CPU measurement is in.

**Architecture:** A Hono API runs in the same Cloudflare Worker that already serves the app, under `/api/*`, so cookies are first-party. Better Auth handles email-code sign-in with users and sessions in D1. The client talks to it with plain `fetch`, and Dexie stays untouched in S1.

**Tech Stack:** Hono 4, Better Auth 1.7.x (email OTP plugin, native D1), Cloudflare Workers + D1, Resend REST API, React 19, Zustand, Vitest 4 (a second `worker` project in Node using wrangler's `getPlatformProxy`), Biome.

**Spec:** `docs/superpowers/specs/2026-11-05-sync-design.md`. Research behind the backend: `notes/reports/Glazette sync backend check.md` (local, not in git).

## Roadmap

| PR | Branch | Delivers | Detailed plan |
|----|--------|----------|---------------|
| S1 | `v2-sync` | Worker API, sign-in by email code, allowed list, interest log, Account button and sheet | This document |
| S2 | `sync-records` | Every table gets a last-changed time; no hard deletes; push/pull of records with later-change-wins; first sign-in merge (name-matching for glazes and clays); sync triggers; "Last synced" in the Account sheet | Written after S1 merges |
| S3 | `sync-photos` | Photos and thumbnails to and from R2 by hash, verified by the server; the waiting count and the dot on the Account button; the sign-out warning | Written after S2 |
| S4 | `recently-deleted` | Recently deleted list and restore; server keeps where each photo was last shown; 30-day clock from when the server first hears of a delete; daily cleanup on a Cron Trigger | Written after S3 |

Decisions that hold across all four PRs:
- Every server read and write is scoped to the signed-in user's id. R2 is never publicly readable.
- Photo bytes never pass through Worker CPU-heavy code: streamed straight to R2, or presigned.
- $0 is firm. If the CPU measurement after S1 shows the free plan's 10 ms limit is too tight, stop and bring Carol the options. Don't move to Workers Paid.

## Global Constraints

- American spelling in code, comments, copy and commits. Don't rename existing British-spelled identifiers.
- The app works exactly as today when signed out. Nothing in S1 touches Dexie, backups or the photo pipeline.
- The app stays at `https://glazette.offhours.workers.dev`.
- Sign in is by a 6-digit code typed into the app. No magic links, no passwords, no other sign-in methods.
- Sessions last 365 days (`expiresIn: 60 * 60 * 24 * 365`), refreshed after 1 day of use (`updateAge: 60 * 60 * 24`).
- Codes: 6 digits, expire after 5 minutes, 3 attempts (Better Auth defaults; set them explicitly).
- Emails are trimmed and lowercased before any lookup or storage.
- Only `allowed_email` rows can get a code. Adding a person is one SQL insert in the D1 console, with no deploy.
- Every turned-away attempt inserts a row into `interest` (email, time).
- Email goes through Resend from `Glazette <onboarding@resend.dev>`. Without a domain, Resend only delivers to the Resend account owner's address, which is Carol's.
- `$0`: Workers Free, D1 Free. No R2 in S1.
- Secrets: `BETTER_AUTH_SECRET` and `RESEND_API_KEY`. Never commit them; local values live in `.dev.vars`, which is already gitignored.
- UI copy (exact):
  - Sheet title: `Account`
  - Signed-out intro: `Sign in to keep your pieces in step across your devices.`
  - Email field label: `Email`; button: `Send code`
  - After sending: `We sent a 6-digit code to {email}.`; field label: `Code`; button: `Sign in`; links: `Send a new code` and `Use a different email`
  - Not on the list: `Glazette accounts aren't open yet. Thanks for your interest!`
  - Wrong code: `That code didn't work. Check it and try again.`
  - Expired or out of attempts: `That code has expired. Send a new one.`
  - Rate limited: `Wait a minute before asking for another code.`
  - Offline: `You're offline. Connect to sign in.`
  - Anything else: `Something went wrong. Try again.`
  - Signed in: `Signed in as {email}`; button: `Sign out`
  - Account button aria-labels: `Account, signed out` and `Account, signed in as {email}`

## Review Focus

1. **The installed app's service worker answering `/api/*` navigations or fetches with `index.html`.** Sign-in would silently break only in the Home Screen app. Expect `/api/*` never to be served by the navigation fallback. Pinned in Task 1.
2. **`Carol@Example.COM ` versus `carol@example.com`.** Expect the same allowed-list match and the same account. Pinned in Task 2.
3. **Resend failing or returning an error.** Expect the sheet to show the generic error, not `We sent a 6-digit code…`. Pinned in Tasks 2 and 3.
4. **Tapping Send code repeatedly, or someone scripting it against Carol's address.** Expect the rate-limit message after the limit, and no flood of emails. Pinned in Task 2.
5. **Opening the Account sheet offline, or with a dead session cookie.** Expect the cached email to still show on the button offline. An expired session (401) signs the device out locally and doesn't crash. Pinned in Task 3.

### Task 2: Sign-in by email code with an allowed list

**Files:**
- Create: `migrations/0001_auth.sql`, `migrations/0002_allowed_and_interest.sql`, `worker/auth.ts`, `worker/email.ts`, `worker/auth.test.ts`
- Modify: `worker/app.ts`

**Interfaces:**
- Consumes: `Env`, `createApp`, `makeTestEnv` (Task 1).
- Produces:
  - `type SendCode = (to: string, code: string) => Promise<void>`.
  - `AppDeps = { sendCode?: SendCode }`. It defaults to `resendSender(env)`.
  - `createAuth(env: Env, sendCode: SendCode)` in `worker/auth.ts`.
  - Mounted at `/api/auth/*`. The client in Task 3 relies on these Better Auth endpoints:
    - `POST /api/auth/email-otp/send-verification-otp` with body `{ email, type: 'sign-in' }`.
    - `POST /api/auth/sign-in/email-otp` with body `{ email, otp }`.
    - `GET /api/auth/get-session`, which returns `null` or `{ user: { email } }`.
    - `POST /api/auth/sign-out`.
  - A turned-away email gets `403` with body `{ code: 'NOT_OPEN' }`.

- [ ] **Step 1: Write the migrations**

- **`0001_auth.sql`:** Better Auth's core SQLite schema (`user`, `session`, `account`, `verification`) plus its `rateLimit` table. Generate it with `pnpm dlx @better-auth/cli generate` against a throwaway SQLite config if the CLI can. Otherwise copy it from Better Auth's documented core schema for v1.7.
- **`0002_allowed_and_interest.sql`:**
  ```sql
  CREATE TABLE allowed_email (email TEXT PRIMARY KEY);
  CREATE TABLE interest (id INTEGER PRIMARY KEY AUTOINCREMENT, email TEXT NOT NULL, attempted_at TEXT NOT NULL);
  CREATE TABLE code_request (email TEXT NOT NULL, requested_at TEXT NOT NULL);
  CREATE INDEX code_request_email ON code_request (email, requested_at);
  ```

`worker/auth.test.ts` uses `makeTestEnv()` and inserts `carol@example.com` into `allowed_email`. Its `sendCode` captures `{ to, code }` in an array. Each request sets `Origin: http://localhost` and a `cf-connecting-ip` header.

- [ ] **Step 4: Implement**

- **`worker/email.ts`:** `resendSender(env): SendCode`.
  - `POST https://api.resend.com/emails` with `Authorization: Bearer ${env.RESEND_API_KEY}` and body `{ from: 'Glazette <onboarding@resend.dev>', to: [to], subject: 'Your Glazette code', text: \`Your Glazette sign-in code is ${code}. It expires in 5 minutes.\` }`.
  - Throw on a non-2xx response.
- **`worker/auth.ts`:** `createAuth`.
  - Base config: `database: env.DB`, `secret`, `baseURL: env.BETTER_AUTH_URL`, `basePath: '/api/auth'`, `trustedOrigins: [env.BETTER_AUTH_URL]`. Local dev sets `BETTER_AUTH_URL` to `https://localhost:5173`, so production never trusts localhost.
  - Session: the Global Constraints values.
  - Plugin: `emailOTP({ otpLength: 6, expiresIn: 300, allowedAttempts: 3, sendVerificationOTP: ({ email, otp }) => sendCode(email, otp) })`. Await the send, so failures surface (Review Focus 3).
  - Rate limits: `rateLimit: { enabled: true, storage: 'database', customRules: { '/email-otp/send-verification-otp': { window: 60, max: 3 } } }`.
- **The gate:** `hooks.before`, via `createAuthMiddleware`, on path `/email-otp/send-verification-otp`:
  1. Normalize the email.
  2. If it isn't in `allowed_email`: insert into `interest` and throw `new APIError('FORBIDDEN', { code: 'NOT_OPEN' })`.
  3. If `code_request` has 5 or more rows for this email in the last hour: throw `APIError('TOO_MANY_REQUESTS')`.
  4. Otherwise, insert a `code_request` row.
  5. Pass the normalized email on in the body.
- **Second guard:** `databaseHooks.user.create.before` refuses an email that isn't on the list.
- **`worker/app.ts`:** mount `app.on(['GET', 'POST'], '/auth/*', (c) => createAuth(c.env, deps.sendCode ?? resendSender(c.env)).handler(c.req.raw))`.
